# 👁 aiWatcher — сторож сервисов WSL2, встроенный в Herdr Control Center

С 25.09.2026 отдельное приложение `D:\My files\aiWatcher` (`watcher_app.py`) **встроено в herdrControlGui**.
Весь его функционал теперь в модуле [`watchdog_manager.py`](../watchdog_manager.py) и в карточке **«aiWatcher»** на странице **«Маршруты»**. Карточка заняла место прежней карточки «Herdr Multiplexer в WSL2».

---

## 1. Что делает aiWatcher

Каждые `interval` секунд (по умолчанию **5**) сторож проверяет два сервиса в WSL2 и запускает упавший:

| Сервис | Порт | Проверка (`check_cmd`) | Запуск (`start_cmd`) |
| :--- | :-: | :--- | :--- |
| **OmniRoute** — шлюз к моделям | 20128 | `ps aux \| grep '[o]mniroute'` | `nohup omniroute start > /dev/null 2>&1 &` |
| **AionUi** — веб-интерфейс и бэкенд `aioncore` | 25808 | пропуск при свежем флаге `~/.aionui-web/.maintenance`, иначе ответ `http://127.0.0.1:25808/` | `tmux new -d -s aionui env -u HTTP_PROXY -u http_proxy -u HTTPS_PROXY -u https_proxy -u ALL_PROXY -u all_proxy NO_PROXY='*' no_proxy='*' /home/f/.local/bin/aionui-web start --no-open --port 25808` |

Команды выполняются через `wsl.exe bash -lc "<команда>"` без окна консоли.

Кроме «жив ли процесс», для AionUi проверяется **здоровье** (`health_cmd`): отвечает ли `/api/auth/status` кодом 2xx–4xx. Если AionUi жив, но отдаёт **502**, в браузере вместо чатов появляется экран входа **«Connection failed, please try again»**. После `heal_after_failures` (3) неудачных проверок подряд сторож сам выполняет **чистый перезапуск** (`heal_cmd` = `aionUi_helper/scripts/fix_aionui_login.py --fix`), не чаще раза в `heal_cooldown_s` (600 с). Подробно — раздел 2а.

Чего сторож **не** делает сам:

- не чинит базу AionUi автоматически, это делает кнопка «🛠 Починить базу AionUi» с подтверждением;
- не следит за прокси, Claude и самим Herdr Control Center.

## 2а. Почему экран входа «Connection failed» не исчезал сам (25.09.2026)

**Симптом.** `http://localhost:25808/#/login` → Sign In → «Connection failed, please try again». Ошибка держалась часами, хотя «сторож работал».

**Цепочка причин:**

1. **03:44 — AionUi запущен вручную из терминала**, а не сторожем. Признак в `~/.aionui-web/aionui.log`: `opened http://127.0.0.1:25808 in your browser` (сторож запускает с `--no-open`). В окружении терминала были `HTTP_PROXY/HTTPS_PROXY=http://127.0.0.1:11015` и `ALL_PROXY=socks5h://127.0.0.1:1015`.
2. Лаунчер `aionui-web` (порт 25808) проксирует `/api/*` на внутренний `aioncore` (`127.0.0.1:45469`). Из-за переменных прокси эти запросы ушли в прокси Claude, и тот вернул **502**: `could not verify admin credentials: /api/auth/status returned 502`. WebSocket `/ws` шёл напрямую, поэтому «что-то работало».
3. **База уже была повреждена** (`database disk image is malformed` с 02:52), а в 04:04 у работающего процесса пропали `-wal`/`-shm`. Все записи после этого идут в удалённый файл и потеряются при перезапуске.
4. **Почему никто не починил:**
   - старый aiWatcher проверял только «есть ли процесс `aionui-web`» — процесс был, значит «RUNNING». Состояние «жив, но 502» он не видел вообще;
   - старый aiWatcher к тому же не запускался из автозагрузки (ошибка в `start_aiWatcher_headless.bat`, исправлена);
   - `repair_aionui.bat` не запускался: новых `before_repair_*` в `~/.aionui-web/db_backups` нет, `aionui-backend.db` не менялся с 04:04;
   - Herdr Control Center с встроенным сторожем нужно было перезапустить, чтобы новый код заработал.

**Что сделано, чтобы это не повторялось:**

- Встроенный aiWatcher проверяет **здоровье** AionUi (`/api/auth/status`), а не только наличие процесса. Прокси из окружения на проверку не влияют (`--noproxy '*'`).
- После 3 неудачных проверок подряд (~15 с) он **сам делает чистый перезапуск** через `fix_aionui_login.py --fix`: под флагом обслуживания, с проверкой, что никто не поднял старый процесс, запуск без прокси.
- Не чаще раза в 10 минут: если причина в битой базе, перезапуск не поможет, и сторож не будет крутиться в цикле. Статус станет «🔴 ЛЕЧЕНИЕ НЕ ПОМОГЛО», в журнале будет подсказка нажать «🛠 Починить базу AionUi».
- Во время загрузки (период прогрева) 502 не считается ошибкой.
- Во время ремонта (флаг `.maintenance`) здоровье не проверяется.

**Что сделать руками один раз, если ошибка есть сейчас:**

1. Перезапустить Herdr Control Center (трей → Выход → запустить), чтобы заработал новый сторож.
2. «Маршруты» → aiWatcher → **🛠 Починить базу AionUi** (база сейчас повреждена), дождаться в журнале `✓ Ремонт базы AionUi: done`.
3. Если после этого статус AionUi не «🟢 РАБОТАЕТ», нажать **♻ Перезапустить AionUi (чисто)**.
4. В браузере открыть `http://localhost:25808` и нажать **Ctrl+F5**.

## 3. Настройки: `watchdog_config.json`

Файл лежит рядом с программой (`D:\My files\herdrControlGui\watchdog_config.json`) и создаётся при первом запуске сторожа.

```json
{
    "watcher_on": true,
    "interval": 5,
    "grace_seconds": 30,
    "apps": {
        "omniroute": { "enabled": true, "check_cmd": "...", "start_cmd": "..." },
        "aionui":    { "enabled": true, "check_cmd": "...", "start_cmd": "..." }
    }
}
```

| Ключ | Значение | Допустимо |
| :--- | :--- | :--- |
| `watcher_on` | включён ли сторож | `true` / `false` |
| `interval` | пауза между проверками, с | 2–600 |
| `grace_seconds` | «прогрев»: сколько секунд после запуска сервис не перезапускается повторно | 0–600 |
| `apps.<имя>.enabled` | следить ли за сервисом | `true` / `false` |
| `apps.<имя>.check_cmd` | bash-команда; код 0 означает «работает» | строка |
| `apps.<имя>.start_cmd` | bash-команда запуска | строка |
| `apps.<имя>.health_cmd` | необязательно: проверка здоровья живого сервиса; код ≠ 0 означает «болен» | строка |
| `apps.<имя>.heal_cmd` | необязательно: лечение больного сервиса (чистый перезапуск) | строка |
| `apps.<имя>.heal_after_failures` | сколько неудачных проверок здоровья подряд до лечения | по умолчанию 3 |
| `apps.<имя>.heal_cooldown_s` | минимальная пауза между лечениями, с | по умолчанию 600 |

Можно добавить свой сервис: любой ключ в `apps` с `check_cmd` и `start_cmd` появится отдельной строкой в карточке после перезапуска программы.

**Импорт из отдельного aiWatcher.** Если `watchdog_config.json` ещё нет, настройки берутся из `D:\My files\aiWatcher\watcher_config.json`. Устаревшие опасные команды AionUi (`ps aux | grep '[a]ionui-web'`, запуск без `--no-open` или без `NO_PROXY`) при этом автоматически заменяются безопасными. Исходный файл не меняется.

Запись конфига атомарная (`.tmp` + замена), так что сбой не оставит пустой файл.

## 5. Переход с отдельного aiWatcher

Два сторожа одновременно запускали бы сервисы дважды. Поэтому встроенный раз в 60 секунд (и по кнопке «Проверить сейчас») ищет процессы `watcher_app.py` и `start_aiWatcher_headless.bat`:

- **Найден внешний aiWatcher.** Встроенный ничего не проверяет и не запускает, статусы показывают `Внешний aiWatcher`, в карточке появляется жёлтое предупреждение.
- **Кнопка «Остановить внешний aiWatcher»** (с подтверждением):
  1. завершает сначала цикл `start_aiWatcher_headless.bat --watchdog` (иначе он через 5 с поднимет python снова), затем `watcher_app.py`;
  2. отключает его автозапуск: `ai_watcher_autorun.vbs` переименовывается в `ai_watcher_autorun.vbs.disabled` в папке автозагрузки Windows. Это обратимо: достаточно вернуть прежнее имя.
- После этого встроенный сторож сразу берёт работу на себя.

Папку `D:\My files\aiWatcher` можно оставить как резерв. Запускать её вместе с Herdr Control Center не нужно.

## 6. История инцидентов (перенесено из `aionUi_helper\docs\AIWATCHER_WATCHDOG.md`)

### 24.09.2026 — AionUi упал и не поднялся

- `aioncore.log`: `Received SIGTERM, shutting down...`, сессия `tmux` закрылась.
- Отдельный aiWatcher не перезапустил сервис: в `DEFAULT_CONFIG` стояло `"watcher_on": False`, конфиг искался относительно текущей папки и терялся.
- Исправлено: абсолютный путь к конфигу, `watcher_on: true`, интервал 10 → 5 с, явный `watcher_config.json`, лаунчер с полным путём к `pythonw.exe` и логом `aiWatcher_error.log`.
- Стресс-тест: `wsl tmux kill-session -t aionui`, через 3 с сторож поднял новую сессию, `/api/assistants/bare:2d23ff1c` вернул 200.

### 25.09.2026 — база AionUi портилась при ремонте

- Ремонт убивал AionUi, сторож через ≤ 5 с запускал его снова, ремонт подменял базу и удалял `-wal`/`-shm` под живым процессом, и база снова становилась `malformed`.
- Исправлено: флаг обслуживания `~/.aionui-web/.maintenance` и проверка AionUi по порту (подробно: `aionUi_helper\docs\LOGIN_CONNECTION_FAILED.md`).

### 25.09.2026 — отдельный aiWatcher не запускался из автозагрузки

- `start_aiWatcher_headless.bat` создавал VBS, который вместо батника перезапускал сам себя (`WScript.ScriptFullName`), поэтому `--watchdog` не выполнялся ни разу (лога `aiWatcher_crash.log` не было).
- Исправлено в батнике (`WScript.Arguments(0)`, CRLF). Окончательное решение — встроенный сторож (этот документ).

### 25.09.2026 — экран входа AionUi «Connection failed»

- После перезагрузки сторож не работал, AionUi запустили вручную из терминала с `HTTP_PROXY/ALL_PROXY`, и внутренние запросы `/api/auth/status` получали 502.
- Встроенный сторож запускает AionUi только с вычищенными прокси-переменными.
- Ошибка держалась и дальше: ни один сторож не видел состояние «жив, но 502», а база оставалась повреждённой. Добавлены проверка здоровья, автоматический чистый перезапуск и кнопки ремонта (раздел 2а).
