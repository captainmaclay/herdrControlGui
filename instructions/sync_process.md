# Процесс синхронизации интеграций исследовательских узлов

В этом документе подробно описано, что происходит в архитектуре Herdr, когда исследователь нажимает кнопки **«Синхронизировать узел B»** или **«Синхронизировать узел A»** в панели Herdr Research Control Center.

---

## 🔵 Синхронизация с узлами Type-B

При нажатии на кнопку синхронизации узла Type-B активируется следующая последовательность шагов:

1. **Проверка и импорт сессионного токена**
   - Если предоставлен путь к новому файлу сессионного токена, система импортирует его в рабочую среду WSL.
   - Если файл не предоставлен, система проверяет наличие и валидность текущей сессии в файле учетных данных.
   - В логах отображаются текущий статус сессии, план и срок действия.

2. **Применение сетевых настроек и Killswitch**
   - Система настраивает файлы конфигурации `settings.json` (как на стороне Windows, так и внутри WSL).
   - Привязывает маршрутизацию к правильному сокету телеметрии (по умолчанию SOCKS5 `:1015`, HTTP `:11015`).
   - Принудительно включает флаг `killswitch`, чтобы предотвратить любые утечки трафика мимо назначенного сокета (для сохранения чистоты экспериментальных измерений).

3. **Патч встроенных ресурсов AionUi**
   - Система регистрирует рабочие ресурсы внутри ядра AionUi, обновляя встроенный исполнимый бинарник узла.
   - Файл манифеста перезаписывается до актуальной версии, чтобы AionUi распознавал рабочий узел.

4. **Регистрация агента в базе данных AionUi**
   - Выполняется синхронизация локальной базы данных AionUi (`aionui-backend.db`, таблица `agent_metadata`).
   - Регистрируется команда запуска, чтобы при вводе задач веб-интерфейс AionUi адресовал запросы в нужный вычислительный узел.

## 🟢 Синхронизация с ансамблем узлов Type-A

При нажатии на кнопку синхронизации узлов Type-A (Ансамбль / OmniRoute) запускаются следующие процессы:

1. **Аудит профилей и портов**
   - Алгоритм обходит все профили, зарегистрированные в сессионном хранилище WSL2.
   - Система опрашивает назначенные последовательные SOCKS5 порты (начиная с `:1081`, `:1082` и т.д.) каждого профиля.
   - Индикатор доступности (`alive: True/False`) показывает, "слушает" ли в данный момент туннель этот порт. 

2. **Регистрация провайдера в базе данных AionUi**
   - Система подключается напрямую к базе `aionui-backend.db` (к таблице `providers`).
   - Проверяется, зарегистрирован ли кастомный провайдер мультиагентного ансамбля.
   - Если он отсутствует, система производит SQL `INSERT` и добавляет провайдера, настраивая `base_url` на локальный балансировщик `http://127.0.0.1:20128/v1` и автоматически его активирует.

3. **Тестовый Ping-запрос (Проверка интеграции)**
   - После настройки базы данных скрипт выполняет контрольный запрос.
   - Он отправляет JSON-запрос к локальному эндпоинту OmniRoute `:20128` (передавая проверочное сообщение "Ping").
   - Маршрутизатор (OmniRoute) выбирает доступный узел из пула (в рамках окон лимитов пропускной способности) и перенаправляет запрос на целевые API.
   - Если возвращается валидный ответ инференса, синхронизация помечается как полностью успешная, и статус выводится в логи.
